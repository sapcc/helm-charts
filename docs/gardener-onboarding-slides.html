Chapter 1 · The Big Picture

Three layers. One goal: manage Kubernetes at scale.

Gardener splits the world into Garden (control room), Seed (hosting substrate), and Shoot (customer cluster). On SAP landscapes they nest inside each other — a Russian doll.

01 · Runtime

Runtime Cluster

rt-qa-de-1 — a plain Kubernetes cluster with real nodes. Hosts the pods that form the garden.

🏢 The building
02 · Garden

Virtual Garden

g-qa-de-1 — a full Kubernetes API, but runs as pods inside the runtime. No dedicated nodes. Stores all declarations.

📋 The control room
03 · Seed

Seed Cluster

mgmt-qa-de-1 — hosts shoot control planes as pods. Real nodes spread across AZs.

🏨 The hotel building
04 · Shoot

Shoot Cluster

cc-b0-qa-de-1 — customer-facing. Control plane is pods in a seed; worker nodes are real VMs / bare metal.

🏃 The hotel guest
Key insight: The garden only holds declarations. All the actual work — creating pods, VMs, network — is done by gardenlet running inside each seed.

Chapter 1 · Deep Dive

The Virtual Garden — a Kubernetes API that lives inside another cluster

There is no dedicated garden cluster with its own hardware. On qa-de-1, gardener-operator runs on the runtime cluster and creates a virtual Kubernetes API as pods:

  • 🟢
    virtual-garden-kube-apiserver — the real k8s apiserver for the garden
  • 🟢
    virtual-garden-etcd-main/events — storage for the garden
  • 🟢
    gardener-apiserver — adds Shoot, Seed, Project APIs on top
  • 🟢
    gardener-scheduler — decides which seed a shoot goes to
  • 🟢
    gardener-controller-manager — cross-cutting controllers
Consequence: If rt-qa-de-1 goes down, the virtual garden goes down. Existing shoots keep running (gardenlet is on the seed), but you cannot create or modify shoots until the garden recovers.

Chapter 1 · ManagedSeed

A seed is just a promoted shoot — the ManagedSeed pattern

mgmt-qa-de-1 is simultaneously a Shoot (Gardener manages its lifecycle) and a Seed (it hosts other shoots' control planes). A ManagedSeed resource is what triggers the promotion.

1

Shoot: mgmt-qa-de-1

Declared in the virtual garden. spec.seedName = rt-qa-de-1. Managed just like any other shoot.

↓
2

ManagedSeed: mgmt-qa-de-1

References the shoot above. Tells Gardener: "once this shoot is Ready, install gardenlet inside it and register it as a Seed."

↓
3

Seed CR: mgmt-qa-de-1

Auto-generated. Never edit it by hand — the next reconcile will overwrite your changes. Edit the ManagedSeed (or the Helm chart) instead.

Where is the Helm chart?

Edit system/cc-shoots-mgmt/templates/managedseed.yaml in sapcc/helm-charts.
Values come from .Values.mgmtShoots — one entry per landscape.

Chapter 1 · Shoot Lifecycle

How a shoot goes from a YAML file to a running cluster

Follow cc-b0-qa-de-1 — a KVM compute shoot on qa-de-1 — step by step.

1

Apply Shoot YAML → virtual garden

The Shoot resource lands in the virtual garden's etcd. Nothing is running yet. Think of it as booking a hotel room on paper.

2

gardener-scheduler picks a seed

Looks at provider type, seed zones, capacity. Writes spec.seedName: mgmt-qa-de-1 onto the Shoot object.

3

gardenlet on the seed picks it up

gardenlet watches shoots where spec.seedName == mgmt-qa-de-1. It now starts reconciling this shoot.

4

gardenlet creates CP namespace on the seed

Namespace: shoot--compute--cc-b0-qa-de-1. Populates it with kube-apiserver, etcd, kcm, kube-scheduler, resource-manager, machine-controller-manager pods.

5

Extension controllers create worker nodes

provider-ironcore-metal creates actual bare-metal servers (the shoot's workers) in the target AZ. Workers talk to the kube-apiserver pod on the seed via Istio ingress.

6

Shoot is Ready ✓

gardenlet reports back to the virtual garden. Workers live on bare metal; their "brain" (CP) lives as pods in the seed namespace.

The shoot's API endpoint is a DNS name → seed's Istio ingress LB → kube-apiserver pod in shoot--compute--cc-b0-qa-de-1.

Chapter 2 · AZ-Local Control Planes (Issue #943)

The problem: shoot control planes land in a random AZ

A seed can span multiple AZs. When gardenlet creates a shoot's CP namespace, it historically picks any node — regardless of which AZ the shoot's workers are in.

Why this breaks things

  • ⚡
    Cross-AZ latency — every kubelet heartbeat crosses an AZ boundary twice
  • 💸
    Cross-AZ traffic cost — at KVM scale this is significant
  • 💥
    Broken blast radius — workers in AZ-B, control plane in AZ-A: an AZ-A outage kills an AZ-B shoot
  • 🌐
    Ingress misplaced — with zonal Istio, the shoot's DNS endpoint follows the CP's AZ, not the workers'
Goal of issue #943: Pin each shoot's CP pods to the same AZ as its worker nodes. Document the approach per cluster type.

Chapter 2 · The Fix

Seed.spec.settings.zoneSelection — the upstream solution

Gardener PR #14238 (merged 2026-03-13) added a new seed setting. When a shoot's CP namespace is created, Gardener intersects the shoot's worker zones with the seed's zones and pins the CP there.

Prefer — best-effort

Intersection non-empty → pin to that zone.
Intersection empty → fall back to random.
Scheduling never fails.

cc-b0 / cc-b1: workers=[1b], seed=[1a,1b] → intersection=[1b] ✅ pinned
cc-d0: workers=[1d], seed=[1a,1b] → empty → random (same as today, no regression)
Enforce — strict

Intersection non-empty → pin to that zone.
Intersection empty → refuse to schedule.

cc-d0: workers=[1d], seed=[1a,1b] → empty → ❌ PermanentlyUnschedulable
Lighthouse: workerless → empty → ❌ same failure
Important caveats: Zone assignment happens at shoot creation. Adding worker zones later does NOT move an existing CP. Workerless shoots (Lighthouse) always have an empty intersection — they need a separate workaround.

How to apply it (via Helm, not by hand)

# system/cc-shoots-mgmt/templates/managedseed.yaml
spec.gardenlet.config.seedConfig.spec.settings.zoneSelection: Enforce

Chapter 2 · The cc-d0 Zone Mismatch

Why we can't use Enforce yet on qa-de-1

During prep for #943 we found that cc-d0-qa-de-1 has workers in qa-de-1d — a zone that doesn't exist on the seed.

1a
3 seed nodes ✅
1b
3 seed nodes ✅
cc-b0, cc-b1 workers ✅
1c
no seed nodes
1d ⚠
no seed nodes
cc-d0 workers here!

Three possible stories

  • 🏗
    Story A: Seed expansion lagging — KVM deployed in 1d but seed nodes haven't followed. Fix: extend seed to 1d.
  • 🐛
    Story B: Shoot misconfigured — someone wrote 1d by mistake. Fix: change worker pool zones to 1a/1b.
  • 🔬
    Story C: Deliberate experiment — 1d prototype. Fix: clarify with the shoot owner.

Decision matrix

ShootPreferEnforce
cc-b0, cc-b1 ✅ pinned to 1b ✅ pinned to 1b
cc-d0 ⚠ random (no regression) ❌ unschedulable!
lh-b (workerless) ⚠ random ❌ unschedulable!
Recommended rollout plan:
  1. Ship Prefer on qa-de-1 first — no regressions, cc-b* get pinned
  2. Investigate cc-d0 mismatch (Story A/B/C?)
  3. Once resolved, flip to Enforce and roll out to other landscapes
Lighthouse is a separate gap. Workerless → intersection always empty → needs a mutating admission policy on the seed to set the zone annotation from the namespace name.

Chapter 3 · Common Gotchas & Recap

Top misconceptions — and what's actually true

MYTH
"The garden is a big physical cluster."
FACT
It's pods inside the runtime cluster. No dedicated hardware.
MYTH
"The shoot's control plane runs in the shoot cluster."
FACT
It runs in a shoot--* namespace on the seed.
MYTH
"The Seed CR is how I change a ManagedSeed's settings."
FACT
Seed is generated — hand edits get overwritten. Edit the ManagedSeed YAML.
MYTH
"kubectl get shoots on the seed shows what it hosts."
FACT
Shoot resources live only in the virtual garden. On the seed look for shoot--* namespaces.
MYTH
"management cluster is a Gardener term."
FACT
It's SAP convention for mgmt-*. Gardener calls it a "seed."
MYTH
"There's only one gardenlet in the landscape."
FACT
Every seed runs its own gardenlet. mgmt-qa-de-1 has one, rt-qa-de-1 has one.
