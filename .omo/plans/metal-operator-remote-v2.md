# metal-operator-remote-v2 - Work Plan

## TL;DR (For humans)

**What you'll get:** A new, much smaller Helm chart at `system/metal-operator-remote-v2/` that replaces `system/metal-operator-remote`. Instead of ~5,500 lines of committed pre-rendered YAML wrapped in Gardener ManagedResource plumbing, `-v2` is a thin wrapper the `dual-deployment-operator` renders twice (once per cluster: seed + shoot) and applies directly. You also get an example operator config (a `DualDeploymentOperator` CR) and a disabled-by-default CR template the deploy pipeline can enable per cluster.

**Why this approach:** The operator already does the "render-twice, transform, apply" work the old Makefile did by hand, so the chart shrinks to the upstream `metal-operator` chart plus a handful of mode-guarded sapcc templates. The BMC credentials are handled cleanly: the chart emits a Secret containing `vault+kvv2://...` reference strings and the in-cluster `secrets-injector` webhook (already on the seed) fills in the real values - nothing secret is committed to git. It stays aligned with the operator team's own per-shoot fixture (upstream emits the webhook config; the operator rewrites its URL).

**What it will NOT do:** No `kube-secrets` pipeline edits, no changes to the `dual-deployment-operator` repo, no upstream version bump, and no changes to the existing `metal-operator-remote` chart (it stays until cutover). NOTE: the operator prerequisite that makes `-v2`'s webhooks work (patch render-scoping / no-op-on-zero-match) is now SHIPPED on operator `main` (Related work) - the CR label `patch` is legal today; the shoot VWC gets the injector label and the seed render no-ops.

**Effort:** Large  **Risk:** Medium - mechanical templating, but a few details need care (the existing sidecar securityContext bug, the sidecar `--target-kubeconfig`, webhook URL/SAN match). Only offline `helm template` verification is in-plan; the live seed+shoot deploy is your separate real-cluster acceptance.
**⚠️ DECOMMISSION - READ FIRST (2026-08-05):** `metal-token-rotate` was **removed** from `metal-operator-remote` upstream by PR [sapcc/helm-charts#12502](https://github.com/sapcc/helm-charts/pull/12502) (chart 0.6.30→0.6.31), replaced by Gardener **WorkloadIdentity** auth for metal infra. This plan was written against the pre-decommission chart (0.6.30). Therefore: the `metal-token-rotate-kubeconfig` Secret (`templates/rotate-kubeconfig.yaml`, now deleted) and the `metal-token-rotate` RBAC (removed from `managedresources/rbac.yaml`) MUST NOT be ported to `-v2`; the token-rotate namespace-alignment "cutover gate" is MOOT. **Rebase this branch onto `origin/master` (which includes #12502) before implementing.** See `.omo/docs/metal-token-rotate-decommission.md` and Related work.
**Decisions to sanity-check:** (1) chart owns the controller-manager Deployment; the upstream subchart Deployment stays disabled. (2) webhook: the upstream subchart emits the VWC and the CR rewrites its URL + stamps the injector label via transforms (matches the operator's metal-operator fixture) - the label `patch` relies on the operator's render-scoping / no-op-on-zero-match behavior, which is now SHIPPED on operator `main` (Related work), so the shoot-only-VWC patch is legal and webhooks work. (3) `remote.ca` dropped; the sole remaining token-requestor Secret (`metal-operator-remote-kubeconfig`) gets its CA from Gardener via `inject-ca-bundle`. (4) macdb creds stay as `vault+kvv2://` refs resolved by secrets-injector.
